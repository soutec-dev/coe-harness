# Security review — `coe-harness` (rama `dev`, alcance `full`)

**Fecha**: 2026-10-06 · **Repo**: `coe-harness` (clon local) · **Checkout revisado**: `dev` en `a7e33fc` + 9 archivos modificados sin commitear (`github-protect.js`, `harness.json`, skills `coe-github`, `CLAUDE.md`, `README.md`, `CHANGELOG.md`, `test/unit.test.js`) · **Remoto**: `soutec-dev/coe-harness` (público, `main` solo con README, sin tags todavía).

## 1. Resumen

El harness está bien construido en lo básico (sin shell en ningún `exec`, argumentos validados, mensajes sin valores sensibles, workflows con permisos mínimos, motor de archivos con write guard y `.new`), pero **el control central —el deny de `git push` a `main` del hook `reglas-pr`— es un parser estático que no coincide con lo que git y el shell resuelven de verdad**: `git push origin HEAD:heads/main`, `HEAD:ma{i,}n`, `HEAD:$(printf main)`, `git -c remote.origin.push=… push` o `git -c push.default=upstream push` llegan a `main` con el hook en silencio, y en repos privados del plan Free (que el README declara soportados) no hay segunda línea del lado de GitHub. Además, el motor del generador borra archivos fuera del repo a partir de rutas `..` en el lockfile (PoC confirmada), el escaneo de secretos es cuadrático en líneas largas y falla abierto, el escaneo commit-por-commit no ve merge commits, la branch protection se sobreescribe (y degrada) en cada `upgrade`, y los guardarraíles son editables por el propio agente.

**Conteo**: Critical 0 · **High 1** · **Medium 8** · **Low 4** · Info 3. No se encontraron secretos ni datos personales reales en el repo (las credenciales de los tests son fixtures marcados).

### Detalle por hallazgo

**H-01 — Evasión del bloqueo de push a `main` (High).** `ramaDeDestino` (`reglas-pr.mjs:309-317`) solo entiende tres formas de destino: `HEAD`, `refs/heads/<x>` y un nombre llano; cualquier otra cosa se considera "no rama". Pero git resuelve destinos sin `refs/` con sus reglas DWIM (`refs/<dst>`, `refs/heads/<dst>`, …), así que `heads/main` es `refs/heads/main`. Resultados del laboratorio (hook ejecutado con JSON por stdin; resolución de git con `--dry-run --porcelain`):

| Comando | Veredicto del hook | Lo que git resuelve | ¿Pide permiso la sesión? |
|---|---|---|---|
| `git push origin HEAD:heads/main` | vacío (permite) | `HEAD:refs/heads/main` | No: coincide con `allow Bash(git push:*)` y con ninguno de los deny (`*:main*` exige el literal `:main`) |
| `git push origin HEAD:ma{i,}n` | vacío | `refs/heads/main` **y** `refs/heads/man` | No documentado que `{…}` fuerce prompt (needs validation) |
| `git push origin HEAD:$(printf main)` | `systemMessage` "el push sigue sin validar" (el refspec partido en dos hace fallar el script → fail-open) | `refs/heads/main` | No documentado (needs validation) |
| `git -c remote.origin.push=HEAD:refs/heads/main push origin` | vacío (`-c` se salta en `:173`, sin refspec ⇒ `HEAD` ⇒ rama actual `fix/x`) | `HEAD:refs/heads/main` | Según docs, `git -c … push` **no** coincide con `Bash(git push:*)`: el hook ni siquiera corre y el comando cae a prompt (o pasa en modos permisivos) |
| `git -c push.default=upstream push` (upstream `origin/main`) | vacío | `refs/heads/fix/x:refs/heads/main` | Ídem |
| `git -C . push origin HEAD:main` | — (el `if` no lo dispara, docs: "a push written another way, such as `git -C . push`, isn't matched") | `main` | Prompt sin razón de denegación |
| alias `git pushmain`, `exec git push …`, `command git push …` | no detectado (`p[1] !== 'push'` / `p[0]` no es git) | `main` | Prompt |
| `git push origin HEAD:main`, `HEAD:refs/heads/main`, `fix/x:master`, `--force`, `-uf`, `+ref`, `--all` | **deny** | — | — |

La misma rama de código hace que el deny de `--force` no vea `git push origin HEAD:ma{i,}n --force-with-lease` como forzado (eso es intencional) ni, más grave, `+HEAD:heads/main` como destino `main`. Remediación mínima en el hook: normalizar `heads/<x>` y resolver el DWIM consultando `git ls-remote --heads origin <x>`; cuando el comando contenga `$`, backticks, `{,}`, globs, remoto distinto de un nombre configurado, `-c`, `-C`, `--push-option`, `--receive-pack`/`--exec` o `--no-verify`, devolver `permissionDecision: "ask"` con el motivo; cuando no haya refspec, calcular el destino efectivo con `git push --dry-run --porcelain <mismos args>` (incluye `remote.<r>.push`, `push.default` y upstream) y denegar si resuelve a `refs/heads/(main|master)`. En `settings.json`, pasar `Bash(git -C *)`, `Bash(git -c *)` y `Bash(git push --no-verify*)` a `ask`. Remediación robusta: instalar desde `init` un hook git `pre-push` (vía `core.hooksPath` dentro del repo) que lea las refs ya resueltas por stdin y rechace `refs/heads/main|master`: es inmune al shell, al DWIM y a la configuración; el único rodeo (`--no-verify`) sí es detectable por texto.

**H-02 — Push a un remoto arbitrario (Medium).** `pushDelComando` toma el primer posicional como remoto y nunca lo valida (`:204`); `prePush` solo evalúa destinos y secretos (`:339-371`), y el escaneo `--not --remotes=origin` considera "ya pusheado" todo lo que exista en `origin/*`. Con `allow Bash(git push:*)` (`settings.json:52`) el comando `git push <URL> HEAD:refs/heads/x` no genera prompt. En el laboratorio el hook devolvió vacío y git resolvió `[new branch]` en el remoto ajeno. Es el camino de exfiltración más barato para una inyección de prompt en un repo privado.

**H-03 — Traversal desde `.claude/harness.json` (Medium).** El barrido de obsoletos (`plan.js:81-97`) toma las claves de `lock.files` tal cual, hace `path.join(cwd, ...dest.split('/'))` y, si el hash coincide, marca `autoPrune: true`; `apply.js:34-43` hace `rmSync` en esa ruta y `saveBackup` (`:78-84`) escribe la copia en `backupRoot + dest`, también con los `..`. El write guard (`:51-54`) no cubre borrados. PoC en scratchpad: con `files["../fuera/sub/victima.txt"] = { hash: <sha del contenido> }`, `upgrade --dry-run` mostró "obsoleto … se borra sin confirmar" y `upgrade --prune --yes` borró el archivo externo e hizo la copia en `repo/.claude/fuera/sub/victima.txt`. Precondiciones: poder escribir el lockfile (está commiteado: basta un PR al repo consumidor; `/.claude/` solo tiene CODEOWNERS advisory, ver H-05) y conocer el contenido del objetivo (archivos con contenido predecible como `.git/HEAD`, o la confirmación tipeada `BORRAR` para el resto, que muestra la ruta). La skill `harness-upgrade` ejecuta `upgrade --prune` sin confirmación intermedia, lo que lo hace explotable desatendido. Mismo tratamiento para `manifest.obsolete` (confiable hoy, pero sin validación).

**H-04 — Degradación silenciosa de la branch protection (Medium).** `PUT /repos/{r}/branches/main/protection` reemplaza toda la configuración; el cuerpo (`github-protect.js:56-69`) fija `required_approving_review_count: 0`, omite `require_code_owner_reviews`, `dismiss_stale_reviews`, `required_conversation_resolution` y cualquier check adicional que la organización hubiera sumado. El paso corre "siempre, sin preguntar" en `init`/`upgrade` (`_shared.js:173-183`). La protección real del repo del generador coincide exactamente con el default, lo que confirma el efecto. Hacer `GET` previo y fusionar solo endureciendo; si la protección existente es más estricta, no tocarla y reportarlo.

**H-05 — El check requerido es neutralizable desde el PR y la revisión del coordinador no está impuesta (Medium).** `reglas-pr.yml` dispara en `pull_request`, hace checkout del merge ref y ejecuta `node scripts/check-pr-rules.mjs` del propio PR (`:34-50`): quien abre el PR controla el check. Con `required_approving_review_count: 0` y sin `require_code_owner_reviews` (`github-protect.js:64`), un usuario con write abre `feature/x → main`, reemplaza el script por `process.exit(0)`, obtiene `reglas-pr` en verde y mergea él mismo (`enforce_admins` no lo impide; `gh pr merge` solo está denegado para el agente). `CODEOWNERS` (`:16-20`) no se aplica sin "require review from code owners", y GitHub lo ignora en privados Free (README `:159`), aunque la skill `datos-sensibles:39-41` y el encabezado de `.datos-autorizados` afirman que cambiarlo "exige revisión del coordinador". `dev` no tiene ninguna protección: un humano o un token comprometido pushea directo y el único check que lo vería es el del PR de release. Esto es consistente con la decisión del ADR §5, pero la consecuencia (check autoeditable) no está documentada.

**H-06 — Guardarraíles editables y autoexención (Medium).** `permissions.deny` (`settings.json:5-50`) solo contiene reglas `Read` y `Bash`; no hay `Edit`/`Write` sobre `.claude/hooks/**`, `.claude/settings.json`, `scripts/check-pr-rules.mjs`, `.datos-autorizados` ni `.github/workflows/**`. La documentación confirma que las reglas `Edit` cubren todas las tools de edición y que el script del hook se lee en cada invocación, así que editarlo surte efecto de inmediato. Además `autorizadosDelRepo()` (`check-pr-rules.mjs:258-264`) lee `.datos-autorizados` del working tree en el momento del check (en CI, el del PR), y el marcador `coe:no-secreto` exime la línea donde está (`:322`): el mismo commit que trae el dato puede traer su autorización. `globARegex('**')` produce `^.*$`. Las instrucciones de las skills ("el agente nunca agrega líneas…") son correctas pero no son un control.

**H-07 — ReDoS → fail-open del gate de secretos (Medium).** `EMAIL = /\b[A-Za-z0-9._%+-]+@…/g` (`:176`) y `url-con-credenciales` (`:101`, `\b[a-z][a-z0-9+.-]*:\/\/…`) son cuadráticos cuando la línea alterna caracteres de palabra y no palabra dentro de la clase (`a.a.a…`, `a-a-a…`, `1.1.1…`): cada posición con `\b` recorre el resto de la línea. Medidas: 20 K → 0,5 s + 1,2 s; 100 K → 19,6 s (`escaneaSecretos`) + 32,9 s (`escaneaDatosSensibles`); 300 K no terminó en 5 minutos. El hook corre el script con `timeout: 45_000` (`reglas-pr.mjs:353`); al vencer, `r.status !== 0 && !== 1` ⇒ `systemMessage` y el push sigue (`:368-370`); el hook completo tiene `timeout: 60` en `settings.json:75` y, según la documentación, un hook que agota su timeout se cancela sin bloquear. `SIN_ESCANEO_DE_CONTENIDO` excluye solo por nombre (`.min.js`, `.map`, `.svg`, lockfiles). En CI el mismo caso cuelga el job hasta `timeout-minutes: 10` (falla cerrado).

**H-08 — Merge commits invisibles (Medium).** `diffSinPushear` y `archivosSinPushear` usan `git log <cabeza> --not --remotes=origin -p/--name-only` sin `-m`/`--diff-merges` (`:473-479`): git no emite diff para merges. Laboratorio: un merge `--no-ff --no-commit` al que se le agregan `.env.staging` y un archivo con una asignación `password` sintética; `git show -m` lista los tres archivos, `git log -p` devuelve 0 líneas, el script da `[OK]` en los tres checks y el hook permite `git push -u origin fix/y`. El check de PR (`origin/dev...HEAD`) sí lo ve mientras el archivo persiste; tras un commit que lo borra, ni el pre-push ni el PR lo detectan y el secreto queda en dos commits del historial. Fix: `--diff-merges=first-parent` en ambos `git log`.

**H-09 — Cadena de suministro (Medium).** Los consumidores ejecutan `npx -y github:soutec-dev/coe-harness#v1` desde la skill `harness-upgrade` (`:17, 26, 37`), que aplica `upgrade --prune` "sin esperar confirmación". `v1` es móvil por diseño (`tag-release.mjs:87`, `push --force`), y el repo no tiene rulesets ni tag protection (verificado), con 6 colaboradores admin y 0 aprobaciones requeridas. Un `git push -f origin v1` desde cualquier cuenta admin (o un workflow con `contents: write` comprometido) ejecuta código arbitrario en cada máquina y pipeline consumidor. Complementos: `npx github:` resuelve `^0.11.0`/`^1.1.1` sin el lockfile del paquete; las acciones van por tag mayor (`actions/checkout@v4`, `actions/setup-node@v4`). Mitigaciones: ruleset sobre `refs/tags/v*` (creación/actualización solo por la app de Actions o el coordinador), tags firmados, que la skill fije `vX.Y.Z` o verifique el SHA esperado, acciones por SHA, dependencias exactas.

**H-10 — Comentarios en PRs ajenos (Low).** `procesar` toma `urlDelPR(JSON.stringify(tool_response))` (`:528`), la **última** URL `…/pull/N` del JSON, y `postPR` hace `gh pr view`, corre los tres grupos con `--pr <url>` y publica `gh pr comment` (`:446-476`) sin comprobar que la URL pertenezca a `origin`; el guard `prDeEsteRepo` existe solo en el modo manual (`:551-555`). Basta `gh pr create … && gh pr view --repo otro/repo 5` (o un `--repo` ajeno en el create, que `cambioDePR` ignora) para comentar en un PR de terceros con la identidad del desarrollador y recibir `decision: "block"` por un PR que no es el propio.

**H-11 — Fail-open (Low).** Toda ruta de error del pre-push termina en `systemMessage` y permite el push (`:368-370`, `:567-569`); el `permissionDecision` solo se usa para `deny`. Convertir "no se pudo verificar" en `ask` mantiene la UX y evita que un error (o un timeout provocado, H-07) sea un bypass.

**H-12 — Falsos negativos (Low).** `pareceSecreto` (`:132-143`) devuelve `false` para cualquier valor con `[\s<>{}()$\`]` (línea 137) —p. ej. una contraseña fuerte con `$$`— y para cualquier valor que contenga `example|sample|dummy|fake|placeholder|changeme|xxxx|your[-_]` (líneas 114 y 139), además de valores < 8 caracteres. Solo se escanean líneas `+` de archivos de texto no excluidos (`:188, 320`): binarios, `.svg`, `.map`, lockfiles y secretos codificados quedan fuera.

**H-13 — Capa de lectura sobrevendida y `gh api` (Low).** La skill `datos-sensibles:108-109` dice "el agente no puede copiar lo que no puede leer", pero las reglas `Read` no se aplican a `cat`/`type` en Bash (docs) y los comandos de solo lectura se auto-aprueban. El deny de `gh pr merge/review`, `gh release` y `gh repo create/delete` (`settings.json:45-49`) no cubre `gh api` ni el MCP de GitHub (la skill `coe-github:233-237` lo reconoce para el hook, no para los deny).

## 4. Dudas / needs validation

1. **Auto-aprobación con metacaracteres**: la documentación no dice si `Bash(git push:*)` auto-aprueba `git push origin HEAD:ma{i,}n` o `HEAD:$(printf main)`. Validar en una sesión real con `--dry-run` (sin tocar el remoto) y observar si aparece prompt. `HEAD:heads/main` no necesita validación: no tiene metacaracteres.
2. **Disparo del `if` en comandos compuestos**: según docs, las reglas se evalúan por subcomando, así que `cd x && git push` debería disparar el hook; `git -C … push`/`git -c … push` no. Confirmar en vivo con `git status && git push --dry-run origin HEAD:heads/x` y `git -C . push --dry-run origin HEAD:heads/x` mirando si el hook se ejecuta.
3. **Timeout del hook (60 s)**: la doc confirma que un hook que agota el tiempo se cancela sin bloquear; no documenta si el usuario ve un aviso. Reproducir con un diff de 100 K caracteres alternados.
4. **`decision: "block"` en PostToolUse**: efecto no documentado (el propio código lo anota, `reglas-pr.mjs:503-504`).
5. **Fuga por mensajes de error de git/gh**: `[ERROR] <primera línea de stderr>` se publica en el comentario del PR (`:468` → `comentario`). No se verificó si git redacta credenciales embebidas en la URL del remoto en `fatal: unable to access '<url>'`; si no lo hace, un remoto con `https://user:token@…` filtraría el token en un comentario público.
6. **Laboratorio git**: las escrituras reales al remoto local fallaron con `unpacker error` (sandbox de esta máquina); la resolución de refspecs se tomó de `git push --dry-run --porcelain`, que la calcula contra las refs anunciadas por el remoto. Contra GitHub, el resultado final depende además de la branch protection (rechaza en públicos/Pro/Team; acepta en privados Free).
7. **PRs desde forks** en `reglas-pr.yml`: `GITHUB_TOKEN` de solo lectura y `gh pr view` sobre repos privados no se probaron.
8. **Permission prompts del propio subagente**: una prueba quedó denegada por las reglas de la sesión (`Bash(git push * main)` dentro de un comando compuesto) y se rehizo sin esa forma; no afecta las conclusiones.

## 5. Controles que sí funcionan (evidencia positiva)

- **Sin inyección de comandos**: todos los procesos se lanzan con `execFileSync`/`spawnSync` y arrays de argumentos, sin shell (`check-pr-rules.mjs:371-400`, `reglas-pr.mjs:262-265`, `github-protect.js:15-22`, `tag-release.mjs:42-48`, `_shared.js:11`), con `GIT_TERMINAL_PROMPT=0`/`GH_PROMPT_DISABLED=1` y timeouts.
- **Argumentos acotados**: `--cabeza` rechaza valores que empiezan con `-` salvo `--branches/--tags` (`:894-897`) y el hook lo pasa como `--cabeza=` (`reglas-pr.mjs:352`); la base se prefija con `origin/` (`:812`); el PR llega a `gh pr view` como número de CI o como URL acotada por regex (`reglas-pr.mjs:256`); el test `--cabeza=--output=pwned.txt` (`check-pr-rules.test.js:510-517`) lo cubre.
- **`SCRIPT_CONFIABLE`**: el hook ejecuta siempre el `check-pr-rules.mjs` del proyecto al que pertenece (`reglas-pr.mjs:282-295`), nunca el del repo destino; el test `hook-reglas-pr.test.js:442-459` lo prueba con un script malicioso que no se ejecuta.
- **Formas canónicas denegadas antes de cualquier escaneo** (`:324-347`): `HEAD:main`, `refs/heads/main`, `rama:main`, `master`, parado en `main` sin refspec, `--force`, `-f`, `-uf`, `+refspec`, `--all`, `--branches`, `--mirror`; el push de un tag sobre un commit con secreto se deniega; `--force-with-lease` queda en `ask` por `settings.json`.
- **Sin fuga de valores**: los `[FAIL]` reportan `ruta:línea (regla)` y rutas (`:574, :586, :605`), nunca el valor; los extractos del body del PR se limitan a 60/80 caracteres del propio autor; `textoParaElAgente` solo devuelve lo que no dio OK.
- **`globARegex` escapa los metacaracteres** (`:243`, verificado con `a[b].csv`, `x(1).csv`, `a|b`); `.datos-autorizados` nunca exime el check de credenciales (solo `escaneaDatosSensibles`, `:343`) y el marcador solo exime el de secretos (`:322`).
- **Workflows**: `pull_request` (no `pull_request_target`), `permissions` mínimos (`contents: read`, `pull-requests: read`), sin interpolación de entradas no confiables en `run:` (número de PR numérico; `base.ref` por `env`), `concurrency` y `timeout-minutes`; `tag-release.yml` solo con `merged == true` y base `main`, checkout de `main` (código ya mergeado), `contents: write` justificado para tags.
- **`github-protect.js`**: `enforce_admins: true`, `strict: true`, sin force-push ni borrado; el nombre de repo sale de `gh repo view --json` y se usa como argumento, no en un shell; errores manejados sin bloquear la instalación y distinguiendo plan Free de permiso faltante (cambio sin commitear revisado).
- **Motor del generador**: write guard sobre escrituras (`apply.js:51-54`), un archivo editado por el usuario nunca se pisa (`.new`), backups byte a byte, `--force` exige tipear `FORCE`, `--yes` nunca implica la confirmación destructiva (`ui.js:60-66`), `--dry-run` puro; `render` es sustitución literal sin evaluación; `merge-json` solo agrega claves; `readLockfile` tolera JSON roto; los `dest` del manifest son relativos y bien formados.
- **Dependencias e higiene**: dos dependencias pequeñas con `integrity` en `package-lock.json` (lockfile v3), sin scripts de ciclo de vida, `engine-strict`, `.npmrc` sin tokens; `.gitignore` gestionado cubre credenciales, volcados, `settings.local.json`, backups y `.new`.
- **Repositorio limpio**: sin tokens, correos ni IPs privadas fuera de `test/`; los fixtures están marcados `coe:no-secreto (fixture)` y registrados en `.datos-autorizados` con justificación; las copias distribuidas en `templates/base/` son idénticas a las de la raíz (`cmp` y test `check-pr-rules.test.js:101-112`).
- **Skills y CLAUDE.md**: las instrucciones son consistentes (no rodear el hook, no autoexentarse, redactar evidencia, PR solo por `gh pr create/edit`, security review delegado a subagente); la superficie de inyección vía `additionalContext`/`permissionDecisionReason` es baja (solo nombres de rama, asuntos de commits propios y extractos cortos del body).
