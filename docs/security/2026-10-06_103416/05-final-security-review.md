### 1. Resumen

Las remediaciones están implementadas y, para **todos los vectores que listó el informe inicial**, funcionan tal como se prometió: el hook normaliza `heads/x`, deniega borrados de `main`, remotos distintos de `origin` y URLs, pide confirmación ante metacaracteres, `git -c`, `--no-verify` y opciones raras, ensaya el push con `git push --dry-run --porcelain --no-verify` y deniega cuando git resuelve `main` por upstream o `push.default`; los `dest` del lockfile fuera del repo se ignoran y `apply` bloquea borrados/respaldos fuera de `cwd`; la protección de `main` se fusiona sin rebajar lo existente cuando el `GET` funciona; `dev` quedó sin force-push ni borrado; el escaneo ve los evil merges, acota las líneas largas y lee `.datos-autorizados` de `origin/dev`; las acciones están fijadas por SHA (verificado contra los tags `v4.2.2` y `v4.4.0`) y el ruleset de tags inmutables existe y está activo.

Sin embargo, **el control central sigue siendo evadible en silencio** con variantes triviales que el ensayo no cubre, porque el ensayo (a) se omite cuando el texto no tiene "cabezas" (`git push origin :` — refspec *matching* — sube `main` si el `main` local está adelantado), (b) se ejecuta sobre el estado **previo** al comando compuesto (`git checkout main && git push origin`, `git config remote.origin.push … && git push origin`), (c) no hereda la configuración que el comando inyecta por entorno (`GIT_CONFIG_COUNT=… git push origin`, `$env:GIT_CONFIG_*; git push origin` en PowerShell) y (d) se queda sin salida con `-q/--quiet`, que el hook interpreta como "no toca main". Los cuatro casos se reprodujeron con el hook real (JSON por stdin) y el `--dry-run` de git confirmó que el destino efectivo es `refs/heads/main`. Dos de ellos coinciden con `allow Bash(git push:*)`, así que no generan prompt. Es el mismo defecto de clase que H-01 (High): el requisito "ningún push cuyo destino efectivo sea `main` pasa en silencio" no se cumple todavía.

Además aparecen regresiones y residuales de severidad media: opciones abreviadas y flags cortos con dígitos (`-4f` fuerza sin que el hook lo vea; `--recei=` se ejecuta durante el ensayo), un tag o rama local llamado `origin/dev` sustituye el `.datos-autorizados` "de dev", el presupuesto interno del hook puede superar su `timeout: 90` (y la documentación confirma que un hook cancelado por timeout **no bloquea**), las reglas de `settings.json` son solo `Bash(...)` y no restringen la tool `PowerShell`, y el detector genérico de contraseñas no reconoce `DB_PASSWORD=` ni `db_password:`.

**Conteo de lo que queda abierto (nuevo o residual)**: Critical 0 · **High 1** (N-01) · Medium 5 (N-02 a N-06) · Low 5 (N-07 a N-11) · Info 2 (N-12, N-13).

**Veredicto del gate (sin Critical/High abiertos): NO.** N-01 es un High abierto. La corrección es pequeña y local al hook (quitar el retorno temprano sin cabezas y tratar `:` como masivo; pedir confirmación cuando el push depende del estado y hay segmentos previos o asignaciones de entorno; neutralizar `-q` en el ensayo y tratar un porcelain vacío como "no verificado"). Con eso y una re-ejecución del laboratorio (`lab.sh` del scratchpad, sección B) el gate puede volver a evaluarse; N-02, N-03 y N-04 conviene cerrarlos en el mismo paso porque son cambios de pocas líneas.

**N-01 — Caminos silenciosos a `main` (High).** La remediación de H-01 apoya la decisión final en el ensayo de git, que es la estrategia correcta, pero tres supuestos no se cumplen. Primero, `prePush` devuelve `null` cuando el texto no deja "cabezas" (`reglas-pr.mjs:463`), antes de las dudas y del ensayo; el refspec especial `:` ("push matching branches") cae ahí: `git push origin :` sube todas las ramas locales que existen en el remoto, `main` incluida si está adelantada (lab B1; el ensayo manual lo muestra: `refs/heads/main:refs/heads/main e70dce6..082c355`). Dejar el `main` local adelantado cuesta un comando de aspecto inocuo (`git fetch origin dev:main`, `git branch -f main dev`, o estar parado en `main` y usar `git merge`, que está en el `allow`). Segundo, el hook mide la rama actual (`:451`) y ensaya (`:506`) **antes** de que corra el comando: en un comando compuesto, `git checkout main && git push origin` o `git config remote.origin.push HEAD:refs/heads/main && git push origin` se evalúan con el estado previo y pasan en silencio (lab B5); solo `cd` se sigue entre segmentos. Tercero, `palabras` descarta las asignaciones de entorno (`:146-148`) sin marcarlas como duda, y el ensayo corre con el entorno del hook, no con el del comando: `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=remote.origin.push GIT_CONFIG_VALUE_0=HEAD:refs/heads/main git push origin` pasa en silencio y git lo resuelve a `HEAD:refs/heads/main` (lab B6, también con `$env:` en PowerShell, donde además el metacarácter `$` queda en otro segmento). Cuarto, `--porcelain` con `-q` no imprime líneas de ref (lab B3: solo `Done`), y un porcelain vacío con remoto explícito se interpreta como "no toca main". `git push origin :` y `git push -q origin` coinciden con `allow Bash(git push:*)` (`settings.json:57`) y ninguno de los deny de `:43-49`, así que no hay prompt. El `--delete` con expansión de llaves (lab B2) es la misma omisión del ensayo aplicada al borrado. La corrección es local al hook y pequeña: ensayar siempre, tratar `:` como masivo, pedir confirmación cuando el push depende del estado y el comando trae segmentos previos o asignaciones de entorno, y neutralizar `-q`.

**N-02 — Abreviaturas y flags cortos (Medium).** git acepta cualquier prefijo no ambiguo de una opción larga y agrupa flags cortos con dígitos (`-4f`). El parser compara nombres exactos (`:217-231`) y `FLAG_CORTO_CON_F` excluye dígitos (`:157`), de modo que `-4f`/`-6f`/`-f4` fuerzan sin que el hook lo vea (lab B4: silencio; el ensayo lo acepta). Más delicado: lo que `OPCIONES_RIESGOSAS` (`:160`) no reconoce viaja tal cual al ensayo (`:416`), que corre antes del prompt de permisos, y git ejecutó el programa dado en `--recei=` como receive-pack del remoto local (lab B4). Con `origin` en HTTPS el efecto es nulo y con SSH lo rechaza el servidor, pero el principio es que el hook ejecuta argumentos del agente antes de la decisión del usuario; conviene una lista cerrada de opciones completas y `ask` para todo lo demás.

**N-03 — Sombra de `origin/dev` (Medium).** `git show origin/dev:…` y `rev-parse --verify origin/dev` (`:273, :286`) usan el nombre corto; el orden de resolución de git prefiere `refs/tags/origin/dev` y `refs/heads/origin/dev` antes que `refs/remotes/origin/dev`. En el laboratorio, una autoexención `**` commiteada en la rama siguió en FAIL (como debe ser) hasta crear un tag o una rama local `origin/dev`: entonces el check pasó a OK y el hook dejó pasar el push de un `nomina-2026.csv`. `resuelveRef` (`:909-911`) tiene el mismo problema para la base del diff del PR. Los tests fijan la ref con `update-ref refs/remotes/origin/dev`, así que no ven el caso. Basta usar los nombres completos.

**N-04 — Presupuesto del hook vs timeout de la plataforma (Medium).** La documentación es explícita: un hook `command` que agota su `timeout` se cancela y "doesn't block the tool call… don't count on a stalled hook to act as a gate". El harness fija 90 s (por debajo del default de 600) y por dentro gasta hasta 45 s **por cabeza** (`:469`), 25 s de ensayo (`:416`) y 10 s por cada llamada auxiliar: con dos refspecs ya se iguala el límite antes de ensayar. Con la medición de N-09 (~1,3 s por línea de 19 K con `@`/`://`), tres ramas con ~27 líneas así cada una mantienen cada escaneo por debajo de su timeout individual y llevan el total a más de 100 s: Claude Code cancela el hook, no hay decisión y el push sigue con el `allow`. La remediación de H-11 convierte en `ask` los errores que el hook ve, pero no este. Hace falta un deadline global propio (menor que el de settings) que devuelva `ask`, y un único escaneo para todas las cabezas.

**N-05 — Tool PowerShell sin reglas (Medium; Low en modo manual).** Todas las reglas de permisos del harness son `Bash(...)`. Según tools-reference, en Windows con Git Bash un deny `Bash(...)` scoped apaga la tool PowerShell "sin aviso" (regresión funcional para la organización, cuya sesión primaria es PowerShell), y si se la reactiva con `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` las reglas `Bash(...)` "no restringen" esa tool: `gh pr merge`, `gh pr review`, `gh release`, `gh repo delete` dejan de estar denegados y `--force-with-lease`, `git -c`, `git reset --hard`, `gh api -X` dejan de pedir confirmación. El hook sí cubre PowerShell (matcher y lab A), por lo que push y PR siguen protegidos; el resto de la capa de permisos no. Espejar las reglas como `PowerShell(...)` es mecánico.

**N-06 — Claves con prefijo (Medium).** El `\b` inicial de `asignacion-de-secreto` (`:110`) exige un límite de palabra justo antes de `password`/`token`/`api_key`…, y `_` y las letras son caracteres de palabra: `DB_PASSWORD=`, `db_password:`, `MYSQL_ROOT_PASSWORD=`, `OPENAI_API_KEY=` (con un valor que no empiece por `sk-`), `DJANGO_SECRET_KEY=`, `export API_TOKEN=`, `smtpPassword =` y `"dbPassword":` no se detectan (`fn.mjs`, valores sintéticos), mientras `password:` y `SECRET_KEY=` sí. Es la forma más común de una credencial fuera de los archivos `.env*` (que sí se frenan por nombre). Un lookbehind `(?<![A-Za-z0-9])` más la transición camelCase lo resuelve sin tocar el resto de la heurística.

**N-07 — `GET` fallido ≠ sin protección (Low).** `proteccionActual` devuelve `null` ante cualquier excepción (`github-protect.js:54-60`); `fusionarProteccion(null)` produce la base y `aplicar` la escribe: un error transitorio de red o un 5xx en el `GET`, seguido de un `PUT` que sí entra, reproduce exactamente H-04. `protegeDev` (`:157-167`) usa el mismo `null` como "no tiene protección" y escribiría la mínima sobre una existente. La fusión además descarta `bypass_pull_request_allowances`, `lock_branch`, `block_creations`, `dismissal_restrictions.apps` y `checks[].app_id`, y el mensaje de éxito (`:199`) afirma que todo se conservó. Distinguir 404 del resto y abortar es el cambio clave.

**N-08 — Validación léxica de rutas (Low).** `destSeguro` compara `partes[0] === '.git'` con distinción de mayúsculas (`plan.js:31`): `".GIT/HEAD"` pasa, y en Windows/macOS apunta al `.git/HEAD` real; su contenido (`ref: refs/heads/dev`) y el hash (`hash.js:11-13`, sha256 truncado del contenido normalizado) son predecibles, así que la entrada es `autoPrune` y `upgrade --prune` —que la skill ejecuta sin confirmación— respalda y borra `.git/HEAD`. `rutaSegura` resuelve con `path.resolve`, no con `realpath`: en checkouts POSIX un symlink commiteado dentro del repo desvía borrado y respaldo fuera de `cwd`. `manifest.dirs` no pasa por ninguna de las dos (`apply.js:39-44`, `verify.js:153`); hoy es entrada confiable, pero la regla debería ser uniforme. Impacto: DoS recuperable (queda copia en `.claude/backup-*/`).

**N-09 — Cuadraticidad bajo el tope (Low).** Con el literal requerido presente, `EMAIL` y `url-con-credenciales` siguen siendo O(n²) por debajo de `MAX_LINEA`: 5 K → 44 ms, 10 K → 290 ms, 19 K → 924 ms (`escaneaDatosSensibles`), y una línea mixta de 19 K cuesta ~1,3 s sumando ambos grupos; 60 líneas (1,1 MB de diff) tardan 77 s y 35 (0,7 MB) agotan los 45 s del script, con lo que el hook pide confirmación (fail-closed, como promete H-11) y CI falla por `timeout-minutes`. El test de H-07 (`check-pr-rules.test.js:236-249`) usa una línea sin `@` ni `://`, justo la que los pre-chequeos descartan, así que no mide el caso costoso. Es un residual aceptable si se documenta, y el insumo de N-04.

**N-10 — Última URL y host (Low).** `urlDelPR` devuelve la última URL `…/pull/N` de toda la respuesta de la tool (`:310-313`) y `prDeEsteRepo` compara solo `owner/repo` (`:651-655`). Un `gh pr create … && echo https://github.com/otro/repo/pull/1` hace que el PR propio no se verifique ni se comente en la sesión (CI sigue corriendo). Elegir la primera URL que coincida con `origin` resuelve ambas cosas.

**N-11 — Formas de `gh api` (Low).** Las reglas `ask` cubren `-X`, `--method`, `-f`, `-F` con espacio (`settings.json:71-74`); `--field`, `--raw-field`, `--input` (POST implícito), `-XPUT` y `--method=PUT` no coinciden. El plan ya asumió cobertura parcial; estas formas son baratas de agregar.

**N-12 / N-13 — Info.** Ver tabla. Destaca que las condiciones del riesgo aceptado H-09 están cumplidas en lo técnico (ruleset activo sin bypass, acciones por SHA verificadas, versión fijable) pero la de 2FA no está documentada ni fue verificable, y que el lockfile del propio repo todavía lleva el nombre de la persona (`.claude/harness.json:20`).

### 5. Dudas / needs validation

1. **`permissionDecision: "ask"` frente a `allow Bash(git push:*)`**: la documentación lista `ask` como valor válido y aclara que las decisiones del hook no eluden las reglas `deny`/`ask` de settings, pero no dice explícitamente que un `ask` del hook prevalezca sobre una regla `allow` coincidente. Toda la remediación de H-01/H-11 depende de eso. Validar en una sesión real con `git push --no-verify origin <rama> --dry-run` (debe aparecer el prompt con el motivo del hook).
2. **Asignaciones de entorno y el allow**: no está documentado si `GIT_CONFIG_COUNT=1 … git push origin` coincide con `Bash(git push:*)`. Si coincide, la variante de entorno de N-01 tampoco prompta; si no, prompta sin motivo.
3. **Estado de la tool PowerShell** en las máquinas consumidoras (Windows con Git Bash): confirmar si el deny `Bash(...)` la apaga (regresión funcional) o si está forzada por entorno (N-05 en su forma de "sin reglas").
4. **Cuerpo fusionado contra la API real** en repos de organización con `restrictions`/`dismissal_restrictions`/`bypass_pull_request_allowances`: solo se verificó el dogfood (sin esos campos). Probar un `PUT` con `--dry-run` no existe; conviene un repo de prueba.
5. **Reproducción temporal de N-04** en una sesión real (tres ramas con diffs de ~0,5 MB de líneas de 19 K) para confirmar que el push sigue tras la cancelación del hook, tal como describe la documentación.
6. **`GCM_INTERACTIVE=never`**: el valor en minúsculas lo acepta Git Credential Manager (no se verificó); si no, un ensayo sin credenciales cacheadas puede abrir UI hasta el timeout de 25 s (termina en `ask`, no en silencio).

**R-01 — Pushes que el hook no modela (High).** El hook decide a partir de un modelo del comando: una secuencia de segmentos donde solo `cd` mueve la carpeta y donde un push es `git [globales] push …` literal. Tres cosas se salen del modelo y, en vez de terminar en `ask`, terminan en silencio. Primero, la carpeta: `carpetaTrasCd` trata `cd -` como "quedarse" (`:200`), no conoce `popd`/`Pop-Location`, y resuelve `cd /c/Users/…` como `C:\c\Users\…`; cuando la carpeta modelada no es un repo con el script, `procesar` hace `continue` (`:838-839`) y no emite decisión. Así, `cd .. && cd - && git push origin` parado en `main`, o `cd /c/…/repo && git push origin` (la forma habitual de encadenar en Git Bash), suben `main` sin que el hook diga nada; el shell real lo confirma (`refs/heads/main:refs/heads/main`). Segundo, el entorno: `queCambia` marca `export`, `set`, `VAR=`, `$env:` y `SetEnvironmentVariable` (`:195-197`), pero no `source`, `.`, `eval` ni una función `git()` definida en el mismo comando; el ensayo corre con el estado del hook y el push real va a `HEAD:refs/heads/main` (lab G, también en PowerShell). Tercero, las indirecciones: `env git push`, `command`, `exec`, `sh -c`, `s=push; git $s`, un alias `git p` (que el README declara como "lo que no ve", pero el agente puede crearlo con `git config alias.p push` en un comando previo), `cmd /c`, `Start-Process`, `Invoke-Expression`. La capa de `settings.json` mitiga solo las formas con `main` literal: según la doc, los deny se evalúan sobre cada subcomando, así que `… && git push origin HEAD:main` cae en `Bash(git push * main)`; pero `git push origin` parado en `main` coincide con el `allow`, y `env git push origin` o `source env.sh; git push origin` solo producen un prompt sin motivo (o nada en modos sin prompt). Es la misma clase y el mismo requisito que N-01, por eso se mantiene High. La corrección es pequeña y queda detallada en la tabla: resolver bien `cd`, pedir confirmación cuando no se pueda resolver, ampliar `queCambia` y pedir confirmación ante cualquier `git` fuera de la posición canónica o con subcomando no literal. Con la regla ya documentada ("el push va solo, en su propio comando"), un enfoque de lista blanca —solo `git push [-u|--set-upstream] origin <rama>` solo en su comando pasa sin preguntar; todo lo demás que contenga `git` y `push` pide confirmación— cerraría la clase entera sin fricción para el flujo normal, y el ensayo seguiría decidiendo el destino real (que, como muestra `pdu/`, puede ser `main` incluso con refspec explícito).

**R-02 — Hooks duplicados por `merge-json` (Medium).** `seedMerge` "solo agrega": con arrays hace la unión de elementos distintos, y una entrada de hook cuyo `timeout` cambió de 90 a 120 es un elemento distinto. La copia dogfood commiteada en `3501be0` lo demuestra: cuatro entradas por evento. No hay impacto directo en la decisión (cualquier deny gana), pero el hook corre dos veces por comando, el PostToolUse publica dos comentarios por PR, y el harness ya no puede corregir un hook existente en los consumidores sin una migración, que hoy no existe (`migrations = []`). El test de espejo mira la plantilla, no la copia local, así que no lo detecta. Es un defecto introducido por el ciclo 2 (el cambio de timeouts) sobre un mecanismo previo.

**R-03 — `origin` redefinido (Medium).** H-02 cerró el remoto por nombre; el ensayo ya informa a dónde iría de verdad (`To ../evil.git`), pero esa información solo se usa cuando el remoto es implícito (`:668-676`). Con `remote.origin.pushurl` o `url.*.pushInsteadOf` puestos en un comando anterior (que `queCambia` sí marcaría si estuviera en el mismo comando), `git push origin fix/x` sale hacia otro repo sin ninguna señal. Comparar siempre la URL del ensayo con la URL de fetch de `origin` cuesta una llamada que el hook ya hace.

**R-04 — Autoexención por `dev` (Medium).** La remediación de H-06 asumió que lo que está en `dev` está revisado; H-16 aceptó el push directo a `dev`. Juntas abren una cadena de dos pushes silenciosos: primero la línea `**` en `.datos-autorizados` a `dev` (el único check que la ve es informativo, `[skip]`), después la rama con los datos. El laboratorio lo reproduce de punta a punta en `lab3` (con el paso remoto simulado por su efecto local exacto, porque el bare del scratchpad falló por longitud de ruta de Windows). Que el grupo `secretos` falle cuando un push desde la sesión toca `.datos-autorizados` es coherente con el principio ya escrito en el hook: "las excepciones las decide el usuario y no el agente".

**R-05 — `GIT~1` (Low).** El cierre de N-08 es correcto para `.GIT`, `..` y los symlinks de directorio (junction hacia fuera bloqueado, verificado). Queda el nombre corto 8.3 de `.git`, que en volúmenes con 8.3 activo (el `C:` por defecto) es una ruta válida a `.git`: `destSeguro` no lo reconoce, `dentroDelRepo` lo considera dentro del repo, y `upgrade --prune` lo borra con respaldo. Mismo impacto que N-08 (DoS recuperable, requiere un lockfile manipulado), misma corrección de una línea tras el realpath.

**R-06 a R-09** — ver tabla. Destaco R-08 porque la doc confirma que los archivos de arranque del shell se aplican a cada comando Bash de la sesión: un `git()` o un `[url] pushInsteadOf` escrito ahí persiste, y la tool `Edit` no tiene deny sobre esos archivos.

### 5. Dudas / needs validation

1. **`permissionDecision: "ask"` del hook frente a `allow Bash(git push:*)`** sigue siendo la pieza clave de toda la remediación y no está confirmada en vivo. La doc (vía subagente, `permissions`): "PreToolUse hook decisions don't bypass permission rules … a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned `allow` or `ask`" — habla de reglas deny/ask de settings, no dice qué pasa entre un `ask` del hook y una regla `allow`; el modelo "los hooks solo endurecen" sugiere que el prompt ocurre. Validar con `git push --no-verify origin <rama> --dry-run` en una sesión real.
2. **Estado de la tool PowerShell con reglas espejo**: la doc (vía subagente, `tools-reference`) dice que un deny `Bash(...)` con alcance "turns the PowerShell tool off for the session … without a warning" y que eso ocurre "without one of these" (no pude leer qué enumera "these"; probablemente una regla `PowerShell(...)` equivalente o la variable `CLAUDE_CODE_USE_POWERSHELL_TOOL`). Si el espejo de N-05 reactiva la tool, el espejo pasa a ser el control que la gobierna y debe mantenerse completo; si la tool sigue apagada, el espejo es inocuo. Validar en una máquina consumidora Windows.
3. **Prompt de `cd` y comandos compuestos**: la doc (vía subagente) indica que "a rule must match each subcommand independently" y que "deny and ask rules apply when any subcommand matches them, including … a command substitution"; no encontré que `cd` esté aprobado por defecto. El impacto real de R-01(a) depende de si los equipos permiten `cd` (habitual). Validar en una sesión real: `cd .. && cd - && git push origin` parado en `main`.
4. **Reglas deny en modos sin prompt** (`bypassPermissions`/`--dangerously-skip-permissions`): no verificado si `Bash(git push * main)` se sigue aplicando; condiciona la mitigación parcial de R-01 para las formas con `main` literal.
5. **`PUT` real de la protección fusionada** en un repo de organización con `restrictions`, `bypass_pull_request_allowances` y `dismissal_restrictions.apps` (N-07): solo verificado por código, tests y lectura del dogfood (`app_id: null`, sin restricciones).
6. **Push real de la cadena R-04 contra GitHub**: el bare del scratchpad rechazó el push por `Filename too long` (ruta > 260 caracteres en el lado receptor; `core.longpaths` y un alias `subst` no lo resolvieron porque Git canonicaliza la ruta real). El efecto local se reprodujo con `update-ref`; conviene repetirlo en un repo de prueba con ruta corta.
7. **Entorno entre comandos**: la doc (vía subagente, `tools-reference`) afirma "Environment variables don't persist. An `export` in one command won't be available in the next" y que el directorio de trabajo sí persiste dentro del proyecto: eso cierra el vector "export en un comando, push en el siguiente", pero conviene confirmarlo en la versión instalada.

No es un límite declarado puro (git es el programa directo y `push` está en el texto; el README promete que un git envuelto pide confirmación), sino un defecto del parser de reach estrecho. El arreglo más limpio es correr `MENCIONA_GIT_PUSH` como respaldo en cada segmento; la variante `@(...)` ya cae en "no literal" → ask, lo que muestra que el camino de sospecha existe y solo falta cubrir el empaquetado por comas.

**S-02 — alias de subcomando antes del push (Medium).** El hook resuelve alias para la invocación de push (`git p` → se analiza como push), pero `queCambia`, que juzga los segmentos previos, no resuelve alias ni marca subcomandos de git desconocidos: `git co main` (con `co=checkout`) devuelve `cambia=null`, así que el push posterior se ensaya con la rama actual (fix/x) y pasa en silencio, mientras el comando real ya hizo `checkout main`. El `git checkout main && git push` literal sí se detecta (control → ask). La vía necesita un alias, que puede preexistir en `.gitconfig` (zona de "lo que no ve") o crearse en un comando previo silencioso (`git config alias.co checkout`). Arreglo de una línea: en `queCambia`, un subcomando de git que no es nativo ni está en las listas → tratarlo como posible cambio de destino (ask).

Ambos son de la **misma meta-clase** que R-01(c) (el hook modela git por subcomando literal y por envoltorio con la palabra siguiente), de impacto alto (push silencioso a `main`) pero probabilidad *accidental* nula —ninguna forma del flujo normal los produce— y con la protección de `main` en GitHub como muro declarado y activo. Por eso Medium, no High. Si el equipo prioriza al agente deliberadamente adversarial dentro de la sesión, súbelos a High y el estado pasa a `NOT READY` hasta cerrarlos.
